# クラウド相談室（仮）

AWS SAA-C03 の学習用シナリオゲーム（非公式）。新人SEとしてお客さんの相談に構成を提案し、Well-Architected の観点で評価されながら知識を身につける。スマホのブラウザで遊べる静的Webアプリ（PWA）。

## 開発

```bash
npm install
npm run dev        # 下書きの相談も含めて起動
npm test           # 評価・復習キュー・条件判定・コンテンツのテスト
npm run build      # 公開用ビルド（確認済みの相談だけを含める）
npx vite preview --port 4173 &   # ビルドしたものを起動
npm run e2e        # スマホ幅のブラウザで通しで遊ぶ確認（Playwright）
```

## 遊び方（会社シム）

小さなクラウド会社の担当として、お客さんのシステムを預かって運用する。会社の暦は全ラックで共通で、時間を進めると全員の運用が同時に進む。

1. タイトル →「はじめから」→ 先輩の話を聞いて社名を決める
2. 机のPCを押すとメールが開く。本編の依頼・スポット案件（復習）・案件メールから、受ける仕事を選ぶ。1組につきラックを1台使う
3. 案件を4ステップで解く
   - ① ヒアリング：用意された質問から選んで聞き、要件メモを埋める（聞き漏らした要件を満たせないと、最初の月の契約料が7割になる）
   - ② 設計：設計図で部品の配置を決める（部品は柏木さんの月の進み具合で解禁：ALB は2か月目、スタンバイとリードレプリカは3か月目）
   - ③ 構築：練習用コンソールで設定を選ぶ
   - ④ 検証：要件ごとに合否が出る
4. 時間を進めると運用が始まる。出来事の日には時間が止まり、障害対応を選ぶ（選んだ対応で停止時間・費用・損害が変わる）
5. 月末の月次報告で、目標の達成度、収支、出来事の理由と出典、障害対応の振り返り、模範の構成を見る
6. 柏木さんの2か月目からは、毎日2〜3件の案件メールが届く（返事の期限は2日）。案件はひな形を組み合わせて自動で作り、どれも予算内で目標をすべて満たせることをエンジンで確かめてある
7. お金の使い道：ラックの増設、運用担当（覚えた障害対応を任せられる）と営業担当（案件メールと報酬が増える）の雇用。契約料の合計で会社のランクが上がる
8. 本編の3人の契約を終えるとクリア画面。そのあとも続けられる

先輩の案内は各画面の初回に出る。点線の下線の用語をタップすると、用語図鑑（公式ドキュメントと照合済み）が開く。メニューから、学習記録・用語図鑑・会社・効果音・タイトルへ戻る、を選べる。セーブはタイトルか会社の画面から、文字列で書き出して別の端末に引き継げる。

復習：月次報告やスポット案件で出会った知識は復習の予定に入り、実際の日付で 1 → 3 → 7 → 14 → 30日の間隔でスポット案件としてメールに届く。

ルールと用語の説明文は、AWSの公式ドキュメントと照合したものだけを公開している（出典と確認日を画面に表示）。練習用コンソールは、画面の構造と設定項目の名前を実際のコンソールに合わせているが、配色・アイコン・ロゴは自作で、AWSとは関係がない。

課題は出題されるのではなく、構成と出来事の組み合わせから発生する。計算に乱数は使わない（案件メールの組み合わせだけは、日付から決まる種で作る）。金額・訪問数・処理能力はゲーム内の値で、実際の料金や性能ではない。

## 構成

```text
content/
  glossary.yaml       用語図鑑（照合済みの説明と出典）
  jobs.yaml           案件メールのひな形（業種・名前・ピークの名前など。AWS の事実は書かない）
  rules.yaml          ルール＝知識の単位（構成のパターン × 出来事 → 何が起きるか）。照合の対象
  spots.yaml          スポット案件（復習用）。合否は運用シムの計算で決まる
  sim/<customer>.yaml お客さんごとの月次計画（訪問数、予算、稼働率の目標、出来事）
  concepts.yaml       学習項目（復習の単位）
  customers.yaml
  cards.yaml          サービス図鑑
  scenarios/          カード式の相談（研修編で使う予定。現在の画面からは使っていない）
scripts/
  validate-content.ts YAMLを検証して src/generated/content.json に書き出す
src/
  sim/                運用シムの計算（engine.ts）、障害対応（incidents.ts）、案件の自動生成（generator.ts）。UIに依存しない純粋関数
  jobs.ts             お客さんの引き当て（本編と自動生成の案件）、日ごとのメール
  guide.ts            先輩の案内と部品の解禁
  sound.ts            効果音（Web Audio）
  engine/             カード式の評価・復習キュー・条件判定
  screens/            タイトル、フロア、メール、会社、案件の4ステップ、月次報告、記録、用語図鑑、クリア、引き継ぎ
  components/pixel.tsx ドット絵の部品（すべて自作）
  components/
```

## ルールを追加・公開するとき

1. `content/rules.yaml` に書く。最初は `review.status: draft`。
2. `src/sim/engine.ts` の `RULE_IDS` に足し、発動する条件を書く。テストも足す。
3. 説明文を公式ドキュメントと一文ずつ照合し、`sources` に出典URLと確認日を入れてから `verified` にする。

`npm run build`（公開用）は、下書きのルールが1件でも残っていると運用シムを含めない。

## 相談を追加・公開するとき

1. `content/scenarios/<id>.yaml` を書く。最初は `review.status: draft`。
2. 解説の事実を公式ドキュメントと一文ずつ照合し、`sources` に出典URLと確認日を入れる。
3. 書いた日とは別の日に読み直してから、`review.status: verified` と `review.verifiedAt` を入れる。

`npm run build` は確認済みの相談だけを含め、学習項目ごとに復習用の相談が2件以上ないと失敗する。

問題や解説を実行時に AI で生成する処理は持たない。実際の試験問題や市販の問題集の文面は使わない。

## 公開

`main` への push で GitHub Actions が GitHub Pages にデプロイする。初回だけ、リポジトリの Settings → Pages → Source を「GitHub Actions」にする。

第1段階（身近な人とのテストプレイ）の間は、デプロイは下書きの相談も含めて公開する（`.github/workflows/deploy.yml`）。
